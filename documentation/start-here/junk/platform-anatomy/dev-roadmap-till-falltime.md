When the form submits, there are several events that are triggered. Right now there are two databases in testing, one is on Airtable and documented, and the other is on PostgreSQL and also documented. There is a toggle method between using either. But if an application is submitted, it should submit to both databases. The code and functions for handling form data should be written developer friendly, so that if we consolidate to one database method, the other is easily deleted. Another event that is triggered is that a Requestor level account (low-permissions, able to view case information about own case) is created in the accounts directory. The log in credentials are shared in a copy pastable format on the confirmation page with a link to log in. This is completely optional for a requestor, but may be helpful to track and expedite the process. A confirmation email is sent to the requestors email, possibly with a copy of their form responses attached. An email alert is also sent to administrative role emails and message inboxes on the platform that a new application has been received. In Profile Settings (not created yet) there should be a checkbox setting for 'Do not send me alerts about incoming applications.' The new form submission is also added to a Queue for Recent Applications, that is viewable by Administrative Roles.

We are also going to consolidate all of the roles (they all still exist, but limiting to about 3-4 permission levels). The very basic role is for Volunteers, Requestors, and Crew Members, and it is to view essential information and do essential tasks for either of those roles. These minimal roles, the essential up to date information is also condensed into an email that they will receive at their listed email, so they don't have to log into the platform at all if they do not wish to. The next level up on permissions is what you could call an Office Worker permission role. This is somebody who is there to work on tasks and manipulate or organize data. Everything action they do or change is logged in the immutable progress tracker. We don't want to have arbitrary permission blocks getting in the way of doing certain tasks, but they may be a necessary evil, that are change-able in Profile Settings from an Administrative Account. We want to err on the side of trust and giving people too many permissions, without crossing the line on creating high level security risks. An office volunteer shouldn't be able to delete an entire table or database.

Then we have Organizational Administrative Roles, which are managerial and supervisory. The roles within the interface are often fluid, and an Organization Administrator can do a variety of tasks relating to Project Management, Bursar Finances, Task Supervision, and Organizationally Relevant Account Management (like modifying permissions). 

The highest permission role is Super-Administrator, which oversees all the organizations and account holders, and is a more technical IT Support role. In this role, you can access every single feature, as well as a sandbox mode, where modifying data to test features is non-destructive.

There is an automatic eligibility checker, which checks for the most simplistic checks, such as under 80% of average median income, is part of organizationally specific demographics, is in eligible geographic areas, has damage sustained by Hurricane Helene, etc. Those that are ineligible still get logged in an Ineligible Repair Log, where if we can get those cases referred to another party that can help, we can. But since different organizations have different criterias, and those may be changing over time, Organizational Admin and Super Administrators need a way in their Profile Settings to dynamically set and change those eligibility criteria. 

The last triggered event when a application is submitted, is that a case directory is created in the Document Bucket. We haven't created a Document Bucket yet. There are document spaces that exist and are used. But we are looking to create a space for this specific to this platform, possibly through an API with Dropbox, or even running a small homemade server in our headquarters from an old laptop, that can receive, save, and broadcast a document archive for users of the platform to access. But we have a template of how this case folder would be structured in repo/elemental-integration/document-generation/document-storage.md

Additionally, it would be helpful to draft out an onboarding portal for when you are starting out and creating the first Super-Administrator upon installation. That way there is a built in method of adding partner Organizations and Accounts without having to manually create that over PostgreSQL. We are right now, testing with two different databases, one of them being Airtable, so having a two-way sync with both methods and an account directory is needed. Currently we haven't integrated the Super-Administrator Dashboard View into the app/ prototype.
